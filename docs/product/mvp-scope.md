# JobLens public MVP scope

Status: accepted by the project owner (2026-09-21).

## Experience

- Visitors can browse currently open Job Listings without signing in. The first geographic scope is Seoul, Gyeonggi, and Incheon across occupations; overseas remote jobs are excluded.
- A Candidate signs in with Google to select Job Preferences, review and sanitize a Resume, discover eligible listings, receive evidence-grounded Job Recommendations when requirements are available, bookmark listings, inspect Recommendation History, and submit Listing Reports.
- Candidates can upload a Korean or English PDF (up to 10 MB and 10 pages) for browser-side text extraction and OCR, or paste resume text. Every route requires Extraction Review and approval before the Sanitized Resume leaves the browser. The original document stays in the browser.
- Role, region, work arrangement, source authorization, original-link availability, and verifiable open recruitment status are deterministic filters. The app does not widen Job Preferences silently; it explains empty results and lets the Candidate change them.
- The interface separates `이력서 근거가 있는 추천` from `조건에 맞는 공고 발견`. Metadata-only and short-snippet listings belong only in discovery, labeled `상세요건 미확인`; preference matches never claim that missing requirements match the Resume. Job Recommendations and deeper Analysis Jobs require usable, analysis-permitted Job Posting requirements supplied by an authorized Job Source. There is no Job Posting paste fallback; Resume-text paste remains available as an alternative to PDF upload.
- Live discovery and resume-grounded recommendation are independently labeled capabilities. Discovery can launch first with appropriately authorized, current listings; if no usable and analysis-permitted full Job Postings or privacy-compliant analysis are available, the interface says that resume-grounded recommendations are unavailable rather than calling discovered listings recommendations.
- After approving a Sanitized Resume, the Candidate explicitly selects `추천 받기`. The service first shortlists Eligible Job Listings with usable, analysis-permitted requirements using explicit Job Preferences and recency, then compares only a bounded subset with the approved Resume; the batch size is set after measuring analysis cost. The interface shows how many eligible candidates existed and how many were actually analyzed (for example, `후보 30건 중 5건 분석`). Unanalyzed listings remain in discovery without an unsuitability judgment. `다음 후보 분석` processes further eligible listings without repeating completed comparisons for the same approved Resume, counts against the same daily limit, and shows the remaining candidates and available analyses. It does not automatically analyze every listing during browsing.
- An analyzed listing needs direct Requirement Evidence for at least one core responsibility or required qualification to become a Job Recommendation. A preferred qualification match alone, or no such evidence, appears separately as `분석했지만 핵심 근거 부족`, not as a recommendation or a judgment of ineligibility. A Candidate may separately request deeper analysis of any selected Eligible Job Listing with usable, analysis-permitted Job Posting requirements, including one not selected in the automatic shortlist; the same privacy and daily cost limits apply.
- Evidence-insufficient Analysis Results are shown only in the current analysis session and are not added to Recommendation History. If the Candidate wants to revisit the listing, they may bookmark it only when its Job Source Permission allows retention.
- During the current browser tab's analysis session, the approved Sanitized Resume remains only in browser memory and may be reused for `다음 후보 분석` and Candidate-selected deep analysis. The Next.js BFF receives it for an active Bedrock invocation but does not keep it for later reuse. Refreshing or closing the tab, signing out, or choosing `이력서 지우기` clears the browser copy and requires a new upload or resume-text paste and Extraction Review. The review screen explains: `승인한 이력서 내용은 현재 탭에서만 다음 분석에 사용됩니다. 분석 요청 중에는 JobLens 서버와 AWS Bedrock으로 전송되지만, 재사용을 위해 서버에 저장하지 않습니다. 새로고침·탭 닫기·로그아웃 후에는 다시 승인해야 합니다.`
- A batch can complete partially. Completed comparisons are shown; failed listings are labeled `분석 실패` and can be retried individually. Validation failures before a model invocation do not consume the daily analysis allowance. Once a paid model invocation starts, the attempt counts even if it later fails, preventing cost-incurring failures from becoming unlimited free retries; the interface shows this rule and the remaining allowance before a retry.
- Recommendation batches, `다음 후보 분석`, retries that start a paid model invocation, and Candidate-selected deep analyses share one Daily Analysis Allowance. It resets at midnight Korea Standard Time, and the interface shows `오늘 사용 횟수/일일 한도` before another invocation. The numeric limit is set only after cost measurement.
- Editing and approving the Sanitized Resume creates a new Resume Version. The same listing may be analyzed again against the new version, but this neither restores the Daily Analysis Allowance nor makes earlier results current. Session results identify their Resume Version; persisted Recommendation History retains only the evidence excerpts used at that time, not the full version.
- Each Resume Version approval screen shows the full Sanitized Resume that will be sent and requires an explicit `이 내용으로 추천 분석` action. Further analyses in the same tab and version do not repeat the consent step, but the AWS transfer notice and `이력서 지우기` action remain visible.
- The browser coordinates each listing comparison without putting Resume content in a durable server queue. Closing or refreshing the tab aborts outstanding browser requests, the BFF attempts to cancel active work, and returned results are discarded; a model invocation that already started may still incur cost and counts against the Daily Analysis Allowance. Only already-completed Job Recommendations can be revisited through Recommendation History.
- Every Resume citation and every cited Job Posting requirement returned by Bedrock is checked against the exact approved Resume Version and source-supplied Job Posting after deterministic whitespace normalization. If any cited text cannot be found, the entire listing result becomes `분석 결과 검증 실패`: it is neither displayed nor saved as a Job Recommendation. Because the model invocation already began, the attempt still counts against the Daily Analysis Allowance.
- Cross-source duplicates are merged only when stable identifiers or a conservative comparison of employer, title, work location, and original employer URL makes identity sufficiently certain. The combined card retains every source and provenance record. Display, retention, and analysis use only data from a source that permits that specific use; permission and content never transfer between duplicate records.
- Requirement categories come only from structured source fields or explicit Job Posting sections such as `주요 업무`, `자격 요건`, and `우대 사항`. Ambiguous requirements are labeled `구분 미상`; AI cannot promote them to core responsibilities or required qualifications, and they cannot by themselves qualify a result as a Job Recommendation.
- If duplicate sources disagree about whether a listing is open or about its closing date, the listing becomes `상태 확인 중` and is excluded from automatic discovery and recommendation until its current status is verified from an authorized reliable source. The service does not select whichever status yields more results.

## Saved data and deletion

- Bookmarked Job Listings remain until the Candidate deletes them, including after closure, provided source retention terms allow it. Closed listings are marked closed rather than recommended again.
- If the Job Source Permission does not allow retaining the listing identity and original link for a bookmark, that listing's bookmark action is disabled with an explanation; the original-link action remains available. The service does not silently store a supposedly user-saved copy of disallowed source data.
- Recommendation History stores listing identity, original link, preferences, reasons, and paired verified Job Posting requirement and approved Resume excerpts. An entry is created only when the Job Source Permission allows retaining the posting citation; otherwise the recommendation is current-session-only, while a separate bookmark remains possible if permitted. History entries expire after 180 days or can be deleted individually. Full Sanitized Resumes, original documents, and deep Analysis Results are not retained.
- Source-supplied listing fields and posting text are stored only within the verified Job Source Permission for that specific use. A source permitted for display but not AI analysis can contribute to discovery, not resume-grounded recommendation; a source not permitted for retention cannot contribute retained source content to bookmarks or history. No Job Posting paste route bypasses these restrictions.
- If a Job Source Permission is withdrawn, the affected new display or analysis use stops immediately. Stored listing content, bookmarks, and Recommendation History that can no longer be lawfully retained or shown are removed, and the Candidate is told why affected saved items disappeared. Unaffected permitted data is not removed merely because a different use was withdrawn.
- The BFF handles approved resume content only in request memory for an active Bedrock invocation. It is excluded from databases, files, caches, queues, application and access logs, analytics, and error-reporting payloads, and references are released immediately after success, failure, or cancellation. An invocation and any unexpectedly surviving temporary processing state expire no later than 15 minutes after the request starts; longer work fails and requires a new request. Browser-memory reuse during the current tab remains under the Candidate's control and is cleared by refresh, tab close, sign-out, or `이력서 지우기`. Account self-deletion removes sessions, bookmarks, and remaining Recommendation History.

## Public release gates

- At least one Job Source must authorize discovery display and supply currently open listings with verifiable original links. Before claiming a useful live multi-occupation discovery release, the enabled sources together must supply at least 20 distinct, currently open Eligible Job Listings across at least two occupations in Seoul, Gyeonggi, or Incheon; regional and occupational coverage is disclosed rather than implied to be comprehensive. The count is an initial launch threshold, not an external fact or a per-Candidate result guarantee. If the live count later falls below it, discovery stays available, displays the actual count and available occupations, and never pads results with expired listings. Until the source and initial inventory gates pass, fixtures are clearly marked as a demo and real automatic discovery is not publicly claimed. Seoul OA-23047 remains a connectivity proof, not an approved public source, because its permission metadata conflicts and it lacks original links.
- Resume-grounded recommendation is activated separately only with Job Postings whose requirements are usable and authorized for analysis, Candidate-approved resume evidence, and the privacy and cost controls below. Availability of discovery alone does not satisfy this recommendation gate.
- Bedrock handles evidence explanations only. Real Candidate content is sent to a model/API verified to support zero retention with in-Region processing in Seoul (`ap-northeast-2`); otherwise AI analysis stays unavailable. The Candidate is told approved text will be sent to AWS. Deterministic filtering remains outside AI.
- Bedrock model invocation logging remains disabled so prompts and outputs are not copied to CloudWatch Logs or S3. Operational telemetry contains identifiers, timing, status, token usage, and cost estimates only, never Resume or Job Posting text.
- Per-Candidate daily analysis limits, spending alerts, and an application-level paid-analysis kill switch are in place before public access. Budget alerts alone are not treated as a hard cap. Listings remain browsable if paid analysis is disabled.
- Candidates can report a stale or incorrect listing. Reports trigger revalidation rather than automatic deletion.
- For transient Job Source connection failures, one automatic retry follows the initial attempt. If it also fails, available sources continue serving verified listings with a partial-availability notice; if all fail, show `현재 공고를 확인할 수 없음`, not `공고 없음`. Authentication or permission errors and exhausted quotas are surfaced without an ineffective retry. Unverified old listings are not used to fill the gap.

## Validation still required

- Source-by-source usage terms, API quotas, attribution, cache/retention rights, and reliable original-link and open-status fields.
- A suitable Seoul in-Region Bedrock model and account-level zero-retention setting, including Korean output quality and actual invocation behavior.
- Measured per-analysis cost and request rate before setting numeric daily limits and spending thresholds.
- Data deletion tests, history access-control and paired-citation tests, ambiguous-requirement classification tests, duplicate-status conflict handling, stale-listing handling, and account deletion behavior.
